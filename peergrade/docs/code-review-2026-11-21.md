## 五、本轮新发现

### 5.1 空草稿 AI 检测会消耗模型调用并污染看板统计（已修复，P1）

- **实测现象：** 以 `{scores:[3,3,3], strengths:"", weaknesses:"", suggestions:""}` 调用 `/api/review-tasks/{id}/ai-check`，返回 200，模型被真实调用一次，该次调用计入教师看板的 `ai_call_count` 与 `ai_success_count`。质量等级分布未被污染（未匹配的检测不进入等级统计）。
- **根因：** `ai_check` 改用 `DraftInput`（允许空字段，以支持 TRD 4.5 的单句低质量样例）后，未再要求三段评语至少有一段非空；前端用 `canCheckAI` 拦住了按钮，但接口本身不设防。
- **风险：** 直接调用接口即可白耗三次额度；看板的「AI 检测调用次数」与「成功次数」会被无意义的检测抬高，削弱答辩时的数据可信度。
- **修复：** 在参数校验段（不占用额度、不调用模型）加入空草稿拒绝：三段评语全空返回 422「请先写下至少一段评价，再进行 AI 检测」。正式提交 `/submit` 的必填约束不变。
- **回归：** `tests/test_regressions.py::test_ai_check_rejects_empty_draft_without_spending_a_call`（断言 422、模型未调用、额度仍为 3、看板调用统计为 0）。

### 5.2 CSV 中只有一份互评时仍给出平均分（待你决策，P2 口径问题）

- **现状：** `互评平均分(15分)` 列在收到 1 份互评时给出该份分数（例如 12.0），`高分歧` 列在不足两份时留空。
- **分歧点：** TRD FR-24 写的是「未评分留空」；而 TRD 3.5 与系统内其他页面把「不足两份互评」统一标记为「评价数量不足」，最终得分按两份取算术平均。导出里出现单一互评的平均分，教师可能误读为最终分。
- **我的意见：** 现状可接受（同行有「收到互评数」列可判断 1 或 2），但与站内口径不完全一致。
- **建议（择一）：** a) 平均分在 `count < 2` 时同样留空；b) 列名改为「现有互评平均分」并在只有一份时加注；c) 维持现状并在技术报告说明口径。默认建议 a，最省事且与反馈页一致。

### 5.3 草稿保存的两种 409 共用同一状态文案（已小幅改进，剩余建议）

- **现状：** 客户端把所有 409 都归入「冲突」状态并展示两个冲突按钮，但「互评已提交或已结束」这类 409 下，冲突按钮无法成功执行。
- **已改：** 服务端草稿版本冲突仍为「conflict」；客户端内部抛出的「互评已结束」改为独立类型，落到「保存失败」状态，并保留准确提示文案。
- **剩余建议：** 若后续要彻底区分，可在服务端为版本冲突使用独立状态码（如 409 与 428 分离），需同步 TRD 第九章的接口约定。

### 5.4 真实模型是否遵守固定标签码尚未验证（外部依赖）

- **现状：** 服务端会把未知标签一律归入 `OTHER`，提示词也已要求四类固定代码。
- **风险：** 若真实模型仍返回自由文本，所有问题都会落进 `OTHER`，看板的「常见问题分布」将失去区分度，而调用统计仍显示正常，问题不易察觉。
- **建议：** 首次真实联调时，用 `python -m tests.check_quality_model --out quality-check.json` 检查原始输出里的 `issues[].type` 是否为四个代码之一，并记录分布；必要时把归一化前的原始类型也存入 `ai_checks.input_data`，便于事后追溯。

### 5.5 浏览器验收依赖未纳入声明（可维护性，P2）

`frontend/scripts/check-v22-browser.cjs` 与 `check-v22b-browser.cjs` 需要 Playwright 与浏览器，`frontend/package.json` 未声明该依赖，只能按 README 手工准备（`PEERGRADE_PLAYWRIGHT`、`PEERGRADE_BROWSER`）。**第三轮已加 npm 入口** `check:browser` 与 `check:browser:classrooms`，脚本可被直接发现与调用；依赖声明仍待补：建议把 `playwright` 列为可选 devDependency 并设置 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`，使 `npm ci` 后可直接执行脚本，或在 CI 中加一条安装浏览器的可选作业。

### 5.6 写接口限流（第三轮已实现，P2 → 已关闭）

- **原状：** 仅登录、注册与班级申请有限流；提交作业、保存草稿、提交互评、AI 检测没有通用限流，TRD 11.2「API 调用增加合理频率限制」未覆盖写路径。
- **已实现：** 按用户设置每分钟预算——提交作业 120、保存草稿 240、提交互评 60、AI 检测 30；超限返回 429 与 `Retry-After: 60`。草稿预算取 240，明显高于 FR-22 自动保存节奏（约 40 次/分钟），正常编辑不会被拦截。
- **实现要点：** 限流计数在取得任务行锁之前执行（独立的计数事务先提交，再由请求事务加锁），避免与 SQLite 的写预留互相等待；沿用既有 `rate_buckets` 原子计数与 `secrets.randbelow` 机会式清理，与登录/注册限流同一路径。
- **回归：** `tests/test_regressions.py::test_write_endpoints_are_rate_limited_per_user`（临时收紧阈值后断言 200/200/429、`Retry-After` 头存在、其他用户不受影响）。

### 5.7 CSV 文件名带任务标识（第三轮已实现，P3 → 已关闭）

`Content-Disposition` 原固定为 `peergrade-results.csv`，连续导出多个任务会产生同名文件。现改为 `peergrade-{任务名 ASCII 化}-{任务ID 前 8 位}.csv`：只保留 ASCII 字母数字与 `-_`，其余字符归一为 `-`，并用任务 ID 保证不同任务不重名。

### 5.8 TRD 接口清单与实现脱节（第三轮已修复，P1）

FR-25/FR-26 落地后实现有 31 个业务 API，而 TRD 第九章仍写「21 个业务 API」且缺班级与复核 10 个接口的说明。已在 TRD 新增 9.5 节「班级与反馈复核」并把计数更正为 31；技术设计报告的接口表此前已同步。

### 5.9 CSV 中只有一份互评时仍给出平均分（待你决策，P2 口径问题）

- **现状：** `互评平均分(15分)` 列在收到 1 份互评时给出该份分数（例如 12.0），`高分歧` 列在不足两份时留空。
- **分歧点：** TRD FR-24 写的是「未评分留空」；而 TRD 3.5 与系统内其他页面把「不足两份互评」统一标记为「评价数量不足」，最终得分按两份取算术平均。导出里出现单一互评的平均分，教师可能误读为最终分。
- **我的意见：** 按 FR-24 字面口径（「未评分」指 0 份互评）当前实现是合规的；差异只在与站内提示语的一致性上。
- **建议（择一）：** a) 平均分在 `count < 2` 时同样留空；b) 列名改为「现有互评平均分」并在只有一份时加注；c) 维持现状并在技术报告说明口径。默认建议 a，最省事且与反馈页一致。
